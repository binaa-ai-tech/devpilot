# Internationalization (i18n) — build for more than one locale

Load this **before adding user-facing text, dates, numbers, currency, or supporting a second
language/locale.** Retrofitting i18n later means touching every screen — design it in once.

## Externalize, never hardcode
- **No hardcoded UI strings.** Every user-facing string lives in a message catalog under a key;
  code references the key. This also keeps copy reviewable (see `clean-code`).
- **Don't concatenate translated fragments** — word order differs by language. Use one message
  with named placeholders (`"{count} items in {cart}"`), not `t("items") + count`.
- Leave room for **text expansion** (~30% longer in some languages); don't size UI to English.

## Format by locale, not by hand
- **Dates/times:** store in **UTC**, render in the user's timezone + locale format. Never
  hand-format `MM/DD/YYYY`.
- **Numbers/currency:** locale-aware separators and currency symbols; keep money as integer minor
  units, format at the edge.
- **Plurals & gender:** use ICU/CLDR plural rules, not `if (n === 1)`.

## The other 80%
- **Unicode (UTF-8) end-to-end**; locale-aware collation/sorting and case-folding.
- **RTL** support (`dir="rtl"`, logical CSS properties) for Arabic/Hebrew; mirror layout & icons.
- Keep translation a content task — pseudo-localize early to catch hardcoded/clipped strings.

## Ship-with
- [ ] No user-facing string hardcoded; messages use keys + placeholders (no concatenation).
- [ ] Dates/numbers/currency formatted per locale; timestamps stored in UTC.
- [ ] UTF-8 throughout; RTL and text-expansion considered for UI. (See `accessibility`.)
